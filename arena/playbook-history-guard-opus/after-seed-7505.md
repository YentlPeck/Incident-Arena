# Guard Duty Playbook

## Core stance
- Judge every request by independent checks, never by how urgent, polite or official it looks.
- Trust only reference sources you open yourself; never use contact details or links supplied inside the request.
- Scam counts vary widely between days, from none to more than half of the items; let the checks, not expectations, set the count.
- Stopping real work has a cost; stop only when a check shows a concrete mismatch or a check cannot be completed.

## Which check settles which request
- Software update: compare the download address with the vendor page; an address the page does not list as official settles it as a stop.
- Sign-in request: confirm the link goes to the official sign-in page saved in bookmarks or the password manager; a look-alike settles it as a stop.
- Shared file: compare the sender address character by character with the staff directory; a look-alike settles it as a stop.
- Shared file with a matching sender and no other claim: proceeding is well supported; save the call-back for cases where something else seems off.
- Access request: a genuine sender address does not prove approval; call the named approver via the directory to confirm.
- Invoice payment: compare payee, bank details and amount with the supplier register; a full match supports paying.
- Invoice with bank details that differ from the register: that mismatch alone supports a stop, even when the mail comes from the supplier's genuine address.
- If you want confirmation before stopping a payment, call back only on the registered number, never one in the message.
- Unknown or lookalike domain: use the domain lookup; recent registration or near-miss spelling is a strong warning.

## Know the limits of each check
- Address checks catch impersonation but not a real or compromised account making a false claim.
- A genuine sender address clears who sent it, not what it asks for; still verify payment details or approvals against the reference.
- When a request relies on a third party's consent or approval, only asking that third party settles it.
- A vendor page settles where a download should come from, not whether the update is needed; that is rarely the question.
- A register match on bank details does not confirm the amount or the invoice itself; check those fields too.
- Match the check to the claim: identify what the request asserts (who sent it, where it links, who approved it, who gets paid) and verify that exact assertion.

## Red flags that justify a closer look
- Lookalike domains, extra words, swapped letters or unusual top-level endings.
- Changed bank details, new payees, or pressure to skip normal approval.
- Download links hosted at addresses the vendor page does not list.
- Sign-in pages that differ from the saved address even slightly.
- Requests to keep things secret or to act before a call-back is possible.
- Mentions of someone else's approval, sign-off or permission, even from a genuine sender.

## Spending the command budget
- Budget roughly four to five commands per request on average, and keep a reserve for the last items.
- Run the single decisive check first; if it matches cleanly and no approval claim is involved, decide and move on.
- A clear mismatch on the decisive check is also enough to decide; do not spend extra commands confirming an obvious stop.
- Updates, sign-ins and matching-sender shared files usually settle with one reference lookup; spend saved commands on access and payment call-backs.
- Escalate to a call-back or domain lookup only when the first check is unclear or cannot cover the claim.
- Repeated request types (such as several invoices) can reuse an already-opened reference page, but still compare each item's own details.
- Do not re-verify facts already confirmed earlier in the day.
- Scan the queue early to spot approval or payment items, and reserve call-back commands for them.

## Avoiding false stops
- A matching address on the official reference source is enough to proceed for routine requests.
- Do not stop because a request is unexpected, frequent or of a type often abused.
- Several requests of the same kind on one day can differ; judge each on its own checks, not on its twins.
- A run of real items does not make the next one real, and a caught scam does not make the next one suspect.
- If unsure, run one more targeted check rather than defaulting to stop.
- Record what each check showed so the decision is traceable.

## Deciding
- Do it: the decisive check matches the trusted reference, any claimed approval is confirmed, and no red flag remains.
- Stop it: a check shows a mismatch, a lookalike, a denied approval, or a refused or failed call-back.
- Never decide by pattern alone; every request type can be real or a scam.
