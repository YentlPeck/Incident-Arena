# Guard Duty Playbook

## Core stance
- Judge every request by independent checks, never by how urgent, polite or official it looks.
- Trust only reference sources you open yourself; never use contact details or links supplied inside the request.
- Scam counts vary from none to more than half of the items; low-scam and high-scam days are both normal, so let the checks, not expectations, set the count.
- Stopping real work has a cost; stop only when a check shows a concrete mismatch or a check cannot be completed.

## Which check settles which request
- Software update: compare the download address with the vendor page; an address the page does not list as official settles it as a stop.
- Sign-in request: compare the link with the official sign-in page in bookmarks or the password manager; a look-alike settles it as a stop, an exact match supports proceeding.
- Shared file: compare the sender address character by character with the staff directory; a look-alike settles it as a stop without a call-back, and a match with no other claim supports proceeding.
- Access request: first compare the requester address with the directory; a look-alike settles it as a stop on its own, and an approver call then only confirms.
- Access request from a matching requester: a genuine sender does not prove approval; call the named approver via the directory, and proceed only when the approver confirms.
- Invoice payment: compare sender, payee, bank details and amount with the supplier register; a full match supports paying, and a call-back on the registered number is a good use of spare budget.
- Invoice with bank details that differ from the register: that mismatch alone supports a stop, even from the supplier's genuine address; any confirming call goes only to the registered number.
- Unknown or lookalike domain: use the domain lookup; recent registration or near-miss spelling is a strong warning.

## Know the limits of each check
- Address checks catch impersonation but not a real or compromised account making a false claim.
- A genuine sender address clears who sent it, not what it asks for; still verify payment details or approvals against the reference.
- A false approval claim from a genuine account recurs day after day, often hidden among real items; only a call-back to the approver exposes it.
- When a request relies on a third party's consent or approval, only asking that third party settles it.
- A vendor page settles where a download should come from, not whether the update is needed; that is rarely the question.
- A register match on bank details does not confirm the amount or the invoice itself; check those fields too.
- Match the check to the claim: identify what the request asserts (who sent it, where it links, who approved it, who gets paid) and verify that exact assertion.
- Scams often stack several mismatches; one clear mismatch is enough, so check the cheapest decisive field first and save budget.
- Look-alike senders and links are the most common scam signal on every request type; run the character-by-character comparison on every item.

## Red flags that justify a closer look
- Lookalike domains, extra words, swapped letters or unusual top-level endings, on any request type.
- Changed bank details, new payees, or pressure to skip normal approval.
- Download or sign-in addresses that differ from the trusted reference even slightly.
- Requests to keep things secret, to act before a call-back is possible, or that cite someone else's approval.

## Spending the command budget
- Budget roughly five commands per request and keep a reserve for the last items; about four to five per item has repeatedly covered full queues with every decision correct.
- Scan the queue early, count the approval and payment items, and reserve one call-back for each before spending on optional confirmations.
- Run the single decisive check first; a clean match with no approval claim, or a clear mismatch, is enough to decide and move on.
- When a look-alike or two independent checks already settle a stop, skip the confirming call-back and bank those commands for approver calls.
- Updates, sign-ins and shared files usually settle with one reference lookup; spend saved commands on access and payment call-backs.
- Repeated request types can reuse an already-opened reference page, but still compare each item's own link or address and make each item's own approver call.
- Never skip the approver call-back on a matching access request to save commands, even after earlier access requests that day were real.
- Never skip the vendor-page or sign-in-page comparison to save commands; a single bad address can hide among otherwise real items.

## Avoiding false stops
- A matching address on the official reference source is enough to proceed for routine requests.
- Do not stop because a request is unexpected, frequent or of a type often abused.
- A queue can be dominated by one request type that splits into real and scam, sometimes with scams first; compare every link fresh and do not let early stops colour later items.
- A run of real items does not make the next one real, and a run of caught scams does not make the next one suspect.
- On a mostly real queue, keep the same check standard for every item; the few scams are found by routine checks, not by heightened suspicion of the rest.
- If unsure, run one more targeted check rather than defaulting to stop.
- Record what each check showed so the decision is traceable.

## Deciding
- Do it: the decisive check matches the trusted reference, any claimed approval is confirmed, and no red flag remains.
- Stop it: a check shows a mismatch, a lookalike, a denied approval, or a refused or failed call-back.
- Never decide by pattern alone; every request type can be real or a scam.
